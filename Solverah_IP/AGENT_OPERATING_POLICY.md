# Solverah — Agent Operating Policy

**Status: active. Read this in full at the start of every unattended run, before doing anything else.**

This file is the standing authority grant for Claude working on Solverah without Sebastian
present. It answers one question: *what may I do on my own, and what must I stop for?* It is
deliberately written as rules with reasons, not as a task list — the task list lives in
`STATE.md`.

If this file and `STATE.md` disagree, this file wins on **authority**; `STATE.md` wins on
**state**.

---

## 0. What "unattended" actually means here

There is no always-on daemon. An unattended run is a **bounded session** started by a schedule
or by Sebastian handing off a task. Each scheduled run starts with **no memory of the previous
one**. Continuity comes entirely from what the last run wrote into the project.

That has one consequence worth internalizing: **an unattended run that produces no written
record produced nothing.** The write-up is not documentation of the work; it is the only part
of the work that survives.

## 1. Run bootstrap — do this before anything else, every run

1. `project_read` **`STATE.md`**. This is the single source of truth for what exists, what is
   open, and what is decided. **Do not open a handoff doc to find out what to do.**
2. `project_read` `AGENT_DECISION_QUEUE.md` — Sebastian may have answered a question from a
   prior run there. **Answers in that file take effect immediately** and are authoritative over
   anything in `STATE.md` or any handoff.
3. Re-read this file's §3 red list before touching anything.

`SOLVERAH_HANDOFF_*.md` files are **history**. Read one only when you need to know *why* a
decision was made or what a past session measured, and only after `STATE.md` has pointed you at
it. Never copy an open item forward out of a handoff — if it is not in `STATE.md` §3, it is not
open.

## 1a. The state discipline — this is load-bearing, not bookkeeping

Two failure modes made this necessary, both real, both found on 2026-08-18:

- A retired rater workbook stayed referenced as a live dependency for several sessions, because
  open items were copy-pasted between dated documents and copy-paste cannot know an artifact
  died.
- A standing item survived seven sessions by gaining emphasis on each restatement instead of
  being checked once. Both of its proposed checks turned out to target retired artifacts.

The root cause was structural: the handoffs were serving as both **log** and **state**. A log is
append-only and immutable; state is mutable and must be *overwritten*. One artifact cannot be
both — a session that needs to correct state can only restate it in a new dated doc, and
restatement is where drift enters. Hence:

- **`STATE.md` is rewritten in place.** Not dated, not versioned, not archived. There is exactly
  one, and correcting it is the normal operation, not an exception.
- **Item IDs (`S-nn`) are permanent** — assigned once, never reused, never renumbered. Every
  cross-reference anywhere uses the ID, never a position. Closed items keep their IDs in §6 so a
  stale reference resolves to "closed" rather than silently to a different item.
- **`carried:` is a defect counter.** Increment it on every open item the run did not touch. **At
  `carried: 5` the item must be closed, re-scoped, or moved to §7 won't-do.** It may not be
  carried again. This is the rule that would have killed the anonymization alarm at session five.
- **Every artifact named anywhere must appear in `STATE.md` §2 with a lifecycle status.** Adding
  a file to the repo or retiring one means updating §2 in the same run. A reference to an
  artifact absent from §2 is unverified — treat it as suspect, not as fact.

## 2. Choosing what to work on

Take the **highest item in `STATE.md` §3 that is not blocked on a human and not on the red
list.** Do not pick the most interesting item. Do not start something new because the top item
looks tedious.

Explicitly: items marked *Blocked on people* are not yours to unblock. Do not draft around
them, do not build a workaround that assumes the blocked answer, do not re-litigate whether
they're really blocked. Surface them (§5) and move down the list.

If every unblocked item is on the red list, **stop and say so** rather than manufacturing work.
A run that reports "everything left needs you" is a correct run, not a failed one.

## 2a. Model recommendation — before starting a task. Stated by Sebastian, 2026-08-19.

Before starting any substantive task, **state which model tier fits it and why — one or two
lines — then get on with it.** The recommendation precedes the work; it never replaces it.

The test is NOT "decisions vs. code." It is **whether the task can be silently wrong**:

- **Heavier tier (Fable / Mythos-class)** — work that is adversarial to its own framing:
  creating, challenging, or correcting a locked decision (D-nn); instrument and scoring design;
  pre-registration and analysis specification; audits of work about to be built on; anything
  whose failure mode is *a plausible value stored forever* rather than a red test. The
  demonstrated case: the S-18 misdiagnosis, where the task arrived with a wrong premise baked
  into its own pre-registered text and the pivotal move was refusing the framing.
- **Lighter tier (Opus / Sonnet-class)** — implementing a decision already written down;
  wiring, test scaffolding, copy changes, refactors under coverage; anything that fails
  loudly. The demonstrated case: the 08-19 WorkPulse swap, executed against constraints the
  docs already carried.
- Rule of thumb inside this project's own vocabulary: **making a D-nn correct is heavy-tier;
  obeying one is light-tier.** When in doubt, price the recommendation against the failure —
  an hour of the heavy model is noise next to a silently broken instrument.

Mechanics, because a session cannot switch its own model:

- **Attended:** give the recommendation before starting; Sebastian switches (`/model`) or waves
  it off. His call is final for that task — do not re-raise it mid-task.
- **Unattended:** proceed on whatever model the run has. If the top unblocked item is
  heavy-tier work and the run is on a light model, prefer the next unblocked light-tier item
  and record the deferral; if nothing light is unblocked, do the work anyway and **lead the run
  record with the mismatch** so the output is read with that discount.
- The state discipline is what makes this split cheap: heavy-tier reasoning serializes into
  D-nn rules and re-scoped items, so light-tier runs can obey documents instead of re-deriving
  them. The known risk on light runs is paraphrase drift (S-35, S-28) — the
  quote-must-match-the-artifact rule binds *especially* firmly there.

## 3. Authority

### GREEN — do it, don't ask

- Write, refactor, and delete production code and tests.
- Run the test suite, `check_assessment_items.py`, and any other local gate or lint.
- Fix bugs found incidentally, including in files unrelated to the current item.
- Read and analyze any artifact in either repo or the project.
- Write new probe/spec/YAML files that are *proposals* (`_PROPOSED` suffix) rather than active.
- Commit to a **branch**. Open a PR. Never to `main` (see red).
- Update `STATE.md` — including closing items, correcting artifact status, and incrementing
  `carried:`. Keeping it accurate is always green.
- Write the end-of-run record (§6).

### YELLOW — do it, but the write-up must lead with it

Reversible decisions where the reasoning matters more than the outcome:

- Adding a new gate rule to `check_assessment_items.py`.
- Choosing between two implementations of equal cost.
- Deciding the enforcement mechanism for an existing rule (e.g. S-04, the seeds rule).
- Restructuring tests, adding coverage, changing test strategy.
- Moving an item to `STATE.md` §7 won't-do under the `carried: 5` limit.
- Drafting outbound communication — the Julie handoff, the I-O review send, any rater notice.
  **Drafted only. Never sent. Never addressed and never queued anywhere that could send it.**

A yellow decision made without recording the alternative you rejected is a red violation. The
rejected option is the part Sebastian needs to audit.

### RED — stop. Do not do these, no matter how obviously correct they seem.

1. **Do not modify `anchors.json`.** Frozen at `v1-frozen-2026-08-15` while raters are
   mid-round. Changing it invalidates work already in strangers' hands. Propose via
   `anchors_v3_PROPOSED.json` only.
2. **Do not spend live API budget.** The 65 deferred company calls (S-10), or any other paid
   run, are an explicit deferred decision. (In the cloud container this is also physically
   impossible — no route to `api.openai.com`. Do not treat the technical barrier as the reason;
   the decision is the reason.)
3. **Do not contact any human.** No email, no message, no PR comment addressed to a person, no
   issue assigned. Julie, George/RATER_B, the two lawyers, and any I-O reviewer are Sebastian's
   to contact. Drafts are yellow; sending is red.
4. **Do not reverse a documented decision.** The list lives in `STATE.md` §4 (D-01…D-18). If a
   decision looks wrong, write the argument into the decision queue — do not act on it.
5. **Do not push to `main`, force-push, rewrite history, or merge your own PR.**
6. **Do not delete files.** Move to `_to_delete/` under the same folder, per existing
   convention, and name what you moved. **Project docs specifically are never deleted by a run**
   — S-27's dedupe is Sebastian's call.
7. **Do not mark an item complete without a passing test that would fail if the work were
   absent.** "I implemented it" is not completion. Rule 3 sat specified-but-unconsumed for a
   full session precisely because nothing failed when it was missing.
8. **Do not write a handoff doc unless explicitly asked.** Standing preference. The end-of-run
   record (§6) and the `STATE.md` update are different, required artifacts.
9. **Do not weaken a contract to make something pass.** Every weakening raises. A silent safe
   default produces data that looks fine and isn't.

## 4. When the answer is genuinely ambiguous

Default to the **reversible** option and keep working. Record it as yellow.

Only stop entirely when *every* path forward is irreversible, or when the ambiguity is about
what Sebastian wants rather than about what is correct. Correctness questions are yours.
Preference questions are his.

## 5. Escalation — how to reach him without becoming noise

Two channels, and the distinction between them is the whole point:

### The decision queue (default — use this ~95% of the time)

Append to `AGENT_DECISION_QUEUE.md` in the project. One entry per decision:

```
## [YYYY-MM-DD run N] <one-line question>
Blocking: <which S-nn stops until this is answered — be specific and honest>
Options:
  A. <option> — consequence
  B. <option> — consequence
Recommendation: <one of them, with the reason in one sentence>
Default if unanswered by next run: <what you'll do — usually A or "keep waiting">
```

Always include a default. A queue entry that stalls the project until he reads it has
reintroduced exactly the bottleneck this whole setup exists to remove.

### The push notification (rare — hard limit of one per run, and most runs send zero)

Send **only** when: work cannot continue at all this run *and* waiting for the next scheduled
run costs something real. Not for progress. Not for "finished the thing." Not for a decision
that has a workable default.

The reason for the hard limit is behavioural, not technical: a notification stream he starts
ignoring is worse than no notification stream, because it will be ignored on the one occasion
it mattered. Guard the channel.

## 6. End of run — always, even if the run accomplished nothing

Two artifacts, in this order:

**First, update `STATE.md`.** Close what closed, add what's new with the next unused `S-nn`,
increment `carried:` on everything untouched, apply the `carried: 5` limit, and update §2 for any
artifact whose status changed. **A run that did work but left `STATE.md` stale has created
exactly the drift this structure exists to prevent** — and the next run, which reads only
`STATE.md`, will act on the wrong picture.

**Then write** `AGENT_RUN_<date>_<n>.md`, under a page:

- What was picked and why.
- **The model recommendation for it (§2a), and — on unattended runs — whether the run's model
  matched.**
- What changed — files, branch name, test counts before/after.
- **Every yellow decision, with the rejected alternative.**
- What was attempted and abandoned, and why. Highest-value section — a future run that
  re-attempts a known dead end has burned a full cycle.
- What is now unblocked that wasn't.
- Anything appended to the decision queue.

## 7. Known hard limits of unattended running — do not work around these

- **No live API access from the cloud container.** Anything requiring `api.openai.com` cannot
  run unattended and must be queued for Sebastian to run locally.
- **No access to the Windows Desktop repos unless the desktop app is open and folders are
  shared.** If the machine is asleep, the only reachable code is what can be cloned from
  GitHub. Unattended work on unreachable code is impossible — say so and pick something else.
- **Notifications are one-way.** A reply cannot reach a scheduled run that has already ended.
  Round-trip latency on any question is at minimum one full cadence period. Design around
  asynchrony; never assume an answer arrives mid-run.
- **Autonomy does not clear human-blocked items.** More agent throughput makes that chain *more*
  load-bearing, not less. Every run should surface it; no run can fix it.

## 8. Amending this file

Changes to §3 are Sebastian's alone — propose them in the decision queue. Changes to §1, §1a and
§6 — the state discipline — may be made only to make it *stricter*; loosening it needs the
decision queue, because every rule there exists in response to a drift failure that already
happened. Everything else may be revised by a run that records the revision in its end-of-run
write-up. (§2a added 2026-08-19 at Sebastian's direction, in-session.)
