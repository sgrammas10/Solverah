BUG 1 — LLM zone normalization never fires
================================================================================

WHAT THE DEBUG SHOWS:
  Raw title "Founder & Full Stack Engineer" → O*NET returns "Engineers, All Other [17-2199.00]"
  resolved=False, reliable=False
  → No "ZONE RESOLUTION — Title Normalization" log entry exists
  → The LLM normalizer is never called

ROOT CAUSE:
  In _resolve_current_zone, after the raw title search returns (1, code, False), the
  code exits early OR the condition that should trigger LLM normalization is wrong.
  The LLM fallback path is gated but never reached.

FIX:
  In _resolve_current_zone, after the raw title attempt results in reliable=False,
  explicitly call _normalize_title_for_onet and try again:

    # Step 1: try raw title
    result = _search_and_resolve(raw_title)
    if result and result[2]:  # reliable=True
        _llm_log("ZONE RESOLUTION — Final Outcome", ...)
        return result

    # Step 2: LLM normalization (whether step 1 found nothing OR found unreliable)
    if openai_client:
        normalized = _normalize_title_for_onet(raw_title, openai_client)
        if normalized and normalized.lower() != raw_title.lower():
            result2 = _search_and_resolve(normalized)
            if result2:
                _llm_log("ZONE RESOLUTION — Final Outcome (via LLM normalization)", ...)
                return result2

    _llm_log("ZONE RESOLUTION — Final Outcome (failed)", "zone=1 resolved=False reliable=False")
    return (1, None, False)

  NOTE: The key change is that step 2 runs even when step 1 found SOMETHING but
  reliable=False. Currently the code likely returns early on any result.

  EXPECTED RESULT after fix:
  - "Founder & Full Stack Engineer" → LLM returns "Software Developers"
  - O*NET finds Software Developers [15-1252.00] → zone=4
  - zone_w becomes non-zero, Web Developers (zone 3, delta=+1) and
    Software Developers (zone 4, delta=0) get boosted over CIRS (zone 5, delta=+1)

  These contaminate the 60-candidate pool and are appearing in top results.

ROOT CAUSE:
  O*NET keyword search is a fuzzy full-text search, not a category search. Searching
  "Data Scientists" returns any role that O*NET's index associates with "scientists"
  or "data". There's no domain filtering applied after search.

  After collecting all O*NET search results, filter out candidates whose SOC code
  starts with prefixes indicating irrelevant domains (for a software-skills user).

  Instead of a hard-coded list (which wouldn't generalize), use a domain inference
  approach based on the user's skills:

  Step A: Infer the user's domain categories from their skills + title.
    - If user has React/TypeScript/Python/JavaScript → tech_software = True
    - If user has biology/chemistry/lab skills → life_science = True
    - If user has patient care/clinical skills → healthcare = True
    - If user has financial modeling/accounting skills → finance = True
    - etc.

  Step B: Build allowed SOC prefixes from active domains:
    DOMAIN_SOC_PREFIXES = {
        "tech_software":  ["11-3", "11-9", "13-11", "15-", "17-2"],
        "cybersecurity":  ["15-12", "15-13", "33-30"],
        "management":     ["11-"],
        "business":       ["13-"],
        "engineering":    ["17-"],
        "data_science":   ["15-2", "13-2", "15-1"],
        "life_science":   ["19-1", "19-2"],
        "healthcare":     ["29-", "31-"],
        "finance":        ["13-2"],
        "legal":          ["23-"],
        "education":      ["25-"],
    }

  Step C: Keep a candidate if its SOC code starts with any allowed prefix.
    - Always allow the SOC codes that O*NET returned for the user's OWN search terms
      (Software Developers → 15-1252 → keep all 15- results)
    - Exclude results whose prefix belongs ONLY to inactive domains

  SIMPLER ALTERNATIVE (implement this first, generalize later):
  After search, score each candidate with a quick domain relevance check:
    - Keep candidate if its SOC prefix matches any of the user's active domain prefixes
    - Discard candidates from life/physical/social sciences (19-1, 19-2, 19-3, 19-4)
      UNLESS the user has domain-specific skills (biology, chemistry, geology, etc.)

  For this specific user (Founder & Full Stack Engineer with tech skills), implement:
    EXCLUDE_IF_NO_MATCHING_DOMAIN = ["19-1", "19-2", "19-3", "19-4"]  # life/physical/social sci
    INCLUDE_ALWAYS = ["15-", "13-", "11-", "17-"]  # CS/IT, business, mgmt, engineering

  Apply this filter in _gather_candidates() after all O*NET searches complete,
  before returning the candidate list.

  EXPECTED RESULT after fix:

  - Bioinformatics Scientists, Remote Sensing Scientists, Atmospheric Scientists

BUG 3 — Coverage metric not differentiating; Software Developers ranks below CIRS
================================================================================

WHAT THE DEBUG SHOWS:
  Computer and Information Research Scientists: centroid=0.9073, coverage=0.4000 → final #1
  Web Developers: centroid=0.8960, coverage=0.4000 → final #3
  Software Developers: NOT in top 5 (final < 0.5238)

  All mainstream tech roles have coverage=0.4000 (2/5 items matched) — flat, no signal.
  Software Developers has 137 role profile items vs CIRS which has fewer, more focused items.
  A large diverse profile → blurry centroid → lower centroid similarity for the user.
  This is backwards: Software Developers should be the best match for a full-stack engineer.

ROOT CAUSE:
  Coverage is computed as: "how many of the TOP-5 items most similar to the ROLE centroid
  does the user match?" The top-5 most representative items of Software Developers'
  centroid are generic abstractions, not concrete tools — they don't match the user's
  specific skill names. CIRS's smaller, more coherent profile produces a tighter centroid
  that happens to score higher.

  Additionally: centroid similarity compresses all tech roles into 0.88-0.91 range
  (everyone looks equally relevant). Coverage was supposed to break this tie but it's
  also flat (all 0.4000).

FIX — Switch coverage direction: measure USER-to-ROLE fit, not ROLE self-representation

  CURRENT (broken): top-K = the K role profile items most similar to the ROLE centroid
    → asks "what are this role's most defining traits?"
    → the user may not have any of those specific traits

  NEW (correct): top-K = the K USER skills most similar to the ROLE centroid
    → asks "among the user's skills, which ones are most relevant to this role?"
    → then check: what fraction of those K skills does the role actually value?
    → this measures "do the user's BEST skills align with what this role needs?"

  Implementation:
    def _coverage_score(user_skill_embeddings: list, role_centroid: np.ndarray,
                        role_item_embeddings: list, k: int = 5) -> float:
        # Find the user's top-K skills most similar to this role's centroid
        user_sims = [(cos_sim(skill_emb, role_centroid), skill_emb)
                     for skill_emb in user_skill_embeddings]
        top_k_user = sorted(user_sims, reverse=True)[:k]

        # For each of those top-K user skills, check if the role values it
        # (i.e., any role item embedding has cosine similarity >= threshold)
        matched = 0
        for sim, skill_emb in top_k_user:
            if sim < _EMBED_THRESHOLD:
                continue  # user skill doesn't even reach threshold with role
            best_role_match = max(cos_sim(skill_emb, r_emb) for r_emb in role_item_embeddings)
            if best_role_match >= _EMBED_THRESHOLD:
                matched += 1

        return matched / k

  This produces genuinely different coverage scores:
    - Software Developers: user's top skills (React, TypeScript, Python, JS) all appear
      in Software Developers' profile → coverage should be 4/5 or 5/5 = 0.8 or 1.0
    - CIRS: user's top skills may not appear in CIRS's profile (research methods,
      formal verification, computational theory) → coverage 1/5 or 2/5 = 0.2 or 0.4
    - This correctly surfaces Software Developers over CIRS

  ALSO: Adjust the final score formula to give coverage MORE weight when zone is
  unreliable (zone_w=0.0). Currently:
    overlap = 0.5×centroid + 0.5×coverage

  Change to:
    overlap = 0.35×centroid + 0.65×coverage

  Rationale: centroid is compressing everyone into 0.88-0.91 and providing no signal.
  Coverage (once fixed with the direction change above) provides the real signal.
  Reducing centroid weight and increasing coverage weight will spread the scores.
