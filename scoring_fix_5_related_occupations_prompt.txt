================================================================================
IMPLEMENTATION PROMPT: Option B — O*NET Related Occupations as Primary Pool
================================================================================

PROBLEM BEING SOLVED
--------------------
The current candidate pool is built by O*NET fuzzy keyword search, which returns
too many semantically adjacent but professionally irrelevant roles (Operations
Research Analysts, Statisticians, CIRS). Filtering these out post-hoc with
hard-coded SOC codes is fragile and field-specific.

SOLUTION
--------
Use O*NET's related occupations endpoint to build the primary candidate pool.
O*NET's relatedness is computed from shared skills, work activities, knowledge,
and work context in the O*NET database — not keyword fuzzy matching. This means
the pool is high-quality by construction, generalizes to any field, and requires
no hard-coded exclusions.

Zone resolution already gives us the user's resolved O*NET code (e.g. 15-1252.00
for Software Developers). That code is the seed. Related occupations for Software
Developers will include Web Developers, Information Security Analysts, Computer
Programmers — NOT Operations Research Analysts or Statisticians.

STEP 2 — Add get_related_occupations() to OnetClient
================================================================================

In backend/services/onet_client.py, add after get_job_zone():

    def get_related_occupations(self, onet_code: str) -> list[Occupation]:
        """Return O*NET-scored related occupations for *onet_code*.

        O*NET computes relatedness from shared skills, work activities,
        knowledge, and work context — not keyword similarity. This produces
        a high-quality, field-appropriate candidate pool without needing
        hard-coded exclusion lists.

        Falls back to empty list on API error so callers can degrade gracefully
        to keyword search.
        """
        try:
            # Use the endpoint path confirmed in STEP 1
            data = self._get(f"online/occupations/{onet_code}/related_occupations")
            # Adjust the key name based on actual probe output
            occs = data.get("occupation", []) or data.get("related_occupation", [])
            return [
                Occupation(code=occ["code"], title=occ["title"])
                for occ in occs
                if occ.get("code") and occ.get("title")
            ]
        except OnetAPIError as exc:
            _log.warning(
                "get_related_occupations failed for %s: %s", onet_code, exc
            )
            return []

STEP 3 — Rearchitect _gather_candidates() in path_scoring.py
================================================================================

CURRENT FLOW:
  1. LLM generates 3 keyword search terms
  2. O*NET keyword search each term → 20 results each → 60 candidate pool
  3. _filter_candidate_pool applies SOC prefix filter → ~40 candidates

NEW FLOW:
  1. If zone resolution gave us a code (current_code is not None):
       PRIMARY pool = onet_client.get_related_occupations(current_code)
  2. LLM still generates keyword search terms (for pivot/supplementary roles)
  3. O*NET keyword search each term → results → SUPPLEMENTARY pool
  4. Merge: primary + supplementary, deduplicate by code
  5. Apply existing _filter_candidate_pool (SOC prefix filter) to merged pool

  If current_code is None (zone resolution failed):
       Fall back to current keyword-only approach (no change to existing behavior)

IMPLEMENTATION in _gather_candidates():

    def _gather_candidates(
        profile: UserProfile,
        onet_client: OnetClient,
        exclude_code: str | None,
        current_onet_code: str | None,   # ← NEW PARAM: from zone resolution
        openai_client=None,
    ) -> list[Occupation]:

        seen: set[str] = set()
        if exclude_code:
            seen.add(exclude_code)

        candidates: list[Occupation] = []

        # ── PRIMARY: O*NET related occupations (high quality, no keyword noise) ──
        if current_onet_code:
            related = onet_client.get_related_occupations(current_onet_code)
            _llm_log(
                "CANDIDATE POOL — Related Occupations",
                f"Seed code: {current_onet_code}\n"
                f"Related ({len(related)}): {[o.title for o in related]}"
            )
            for occ in related:
                if occ.code not in seen:
                    seen.add(occ.code)
                    candidates.append(occ)

        # ── SUPPLEMENTARY: LLM keyword search (for pivots, Bright Outlook, etc.) ──
        search_terms = _generate_search_terms(profile, openai_client)
        for term in search_terms:
            results = onet_client.search_occupations(term)
            _llm_log(
                f"CANDIDATE SEARCH — Term: {term!r}",
                f"Results ({len(results)}): {[o.title for o in results]}"
            )
            for occ in results:
                if occ.code not in seen:
                    seen.add(occ.code)
                    candidates.append(occ)

        # Existing filter (SOC prefix inclusion) still applies
        filtered = _filter_candidate_pool(candidates, profile)

        _llm_log(
            "CANDIDATE POOL — Final",
            f"Total candidates: {len(filtered)}\n"
            + "\n".join(f"  [{o.code}] {o.title}" for o in filtered)
        )
        return filtered

Also pass current_onet_code into _gather_candidates from score_paths():

IF THE RELATED OCCUPATIONS ENDPOINT DOES NOT EXIST
================================================================================

If the probe in STEP 1 confirms no related occupations endpoint exists in v2:

  FALLBACK OPTION: Use job family occupations as the primary pool.
  OnetClient.get_job_family_occupations() already exists and is tested.

  The user's resolved O*NET code (e.g., 15-1252.00) → family code = "15-0000"
  (Computer and Information Technology Occupations)

  get_job_family_occupations("15-0000") returns ALL ~50 occupations in the 15-
  family. This is broader than related occupations but much better than keyword
  search — it's at least field-scoped. Operations Research Analysts (15-2031)
  and Statisticians (15-2041) are in 15-2, not 15-1, so they'd still appear.

  In this case: use job family + apply the minimal SOC sub-prefix exclusion
  (exclude 15-2xxx from tech profiles) since we're already scoped to one family.
  This is a much narrower exclusion than the original hard-coded list approach —
  just one SOC minor group rather than 14 specific codes — and is defensible
  because 15-2 (Mathematical Science Occupations) is a genuinely distinct
  professional track from 15-1 (Computer Occupations).

  In either case: update this prompt with findings and proceed accordingly.
